Why: a report with no findings is only reassuring if the scanners really ran. This shows which scanners ran, were skipped, failed or reused an earlier report.

Example: a pull request shows 0 findings, but the details say the PMD scanner was skipped for an unsupported language, so Java files were not checked.

You need: Scan Results View. Historical scans may say Not recorded.

call_mergeMerge gate: merges before a scan finishedWhy · example · what you need · steps

Why: before making Watchtower block merges, you need to know how often code is merged before its scan completes.

Example: commit abc is pushed at 10:00 and merged at 10:02 while its scan is still queued — it counts as “Scan in progress”.

You need: Scan Results View. Scripts can read the same figures as JSON from /rest/scan/result/merge-gate?days=30 with an API key.

  1. Pick a window: the last 7, 30 or 90 days.
  2. Read the chips: merges in the window, merges with no completed scan of the merged commit (scan in progress, newer commit not scanned, scan failed, never scanned), and merges whose scan blocked (bypassed or not).
  3. Open Top repositories to see where to enforce first, then follow a row to the pull request in Bitbucket.

Merges are counted from the release that started recording how pull requests close; older merges show as Resolved.

Review findings

rate_reviewFinding feedbackWhy · example · what you need · steps

Why: a scanner cannot tell whether its own match is right. A person's judgment is the evidence that shows which rules are noisy and which are trustworthy.

Example: a hard-coded password rule fires on a test fixture. You mark it False positive with handling Test code, so the rule's health counts it and the team can scope the rule.

You need: Scan Results View and Finding Feedback, plus a saved finding record.

  1. Open a pull request, upload or repository scan report and select a finding.
  2. Choose Review finding. A dialog shows the rule, severity, file and line without leaving the report.
  3. Choose True positive for a correct detection, False positive for an incorrect detection, or Unknown when you cannot decide, then how to handle it, such as Action required or Accepted risk, with a short explanation.
  4. Save. The report updates the review marker while keeping the same filter and finding; reopen the dialog to edit your decision or see its history.

Ask AI (advisory): when an Assistant Admin turns on AI finding assessment, people with Assistant Use and source access can ask for a second opinion on one selected finding. It reads the code around the finding at the scanned commit and answers likely true positive, likely false positive, needs review or insufficient evidence, with four named checks and the lines it relied on. Your judgment is what counts; the answer never changes the finding. Findings of rules that detect secrets, lines where a secret was recorded and uploaded code are never sent.

Accepting a risk can still mean the detection is correct. Feedback supplies review evidence; it does not bypass a PR, change a rule, or train the AI automatically.

Open PR results, upload results, or repository scans.

lock_openPR bypass reason categoriesWhy · example · what you need · steps

Why: sometimes a pull request must merge despite a blocking finding. A bypass records who allowed it and why, so exceptions stay visible and auditable.

Example: a release fix is blocked by a finding the team accepts until next sprint. They request a bypass with reason Accepted risk; an approver applies it and the pull request can merge.

You need: Scan Results View; request and approval actions depend on your permissions and the PR's state.

  1. On a blocking PR report choose Bypass, select a reason category and explain the request.
  2. Send the request, or apply a bypass if you have PR Scan Bypass permission.
  3. Record finding feedback separately when the finding itself is wrong: a bypass reason alone does not label findings or change rule health.

An approved bypass affects blocking only for that pull request.

Improve rules

playlist_add_checkRule work: what needs a personWhy · example · what you need · steps

Why: evidence about rules is spread over findings, reviews, candidates and settings. Rule work lists, in one place, what needs a person and links to where to do it.

Example: Regex rule 31 has 10 reviewed findings and 8 were false positives. It appears under Rule investigations; Investigate rule opens its health, and a candidate fix then appears under Candidates until it is promoted or rejected.

You need: Rule Modify or Ruleset View. Findings to review and Rule investigations also need Scan Results View; candidates and editing need Rule Modify.

  1. Findings to review: rules that matched recently but have too few reviewed findings to judge. Open a recent report from the row and review its matches.
  2. Rule investigations: rules whose reviewed findings are mostly false positives.
  3. Assigned and overdue reviews, and Candidates waiting for tests or a decision.
  4. Setup gaps: missing owner or CWE, or no recent matches although the engine ran. These are kept apart because they are not proof a rule is wrong.

monitor_heartRule healthWhy · example · what you need · steps

Why: to decide whether a rule needs fixing, using how often it matched and what reviewers said about those matches.

Example: 6 of 8 reviewed findings in 90 days were false positives, so health shows Needs review; with only 2 reviewed it shows Insufficient data instead.

You need: Scan Results View, plus Rule Modify or Ruleset View.

  1. Open Rule health from Rule work or from the selected rule in Rule Editing.
  2. Choose the rule revision, time window, scan scope and finding policy.
  3. Compare findings and reviewed labels, then check the coverage notes. No eligible evidence, unverified zero matches and successful zero matches are explained separately.
  4. Start a saved review or test an improvement when the evidence supports it; health never changes enforcement by itself.

The false-positive rate is FP ÷ (TP + FP) among reviewed findings; Unknown labels are separate. Insufficient data/coverage means more evidence is needed, not that the rule is bad. Old findings may have unknown revisions, and reused reports are excluded.

Why: to assign someone to investigate a rule and keep their recommendation and decision with the evidence.

Example: the owner is asked to check a noisy rule; they record “scope to src/ only” and accept the review, which can then become approved knowledge or a candidate.

You need: Rule Modify or Ruleset View to read; Rule Modify to save.

personRule owner and statusWhy · example · what you need · steps

Why: every rule needs someone accountable and a date to look at it again; status decides whether it still runs.

Example: the platform team owns the SQL injection rules with a review every six months; an outdated rule is set to Being phased out while its replacement is tested.

You need: Rule Modify.

  1. In Rule Editing select a rule and choose Owner and status.
  2. Enter an owner or team and the next review date, and optionally weakness IDs such as CWE-79.
  3. Choose Active, Being phased out (keeps running while a replacement is reviewed) or Retired (excluded from future scans), then save.

A status change affects future scans; past results remain available.

scienceTest rule improvementsWhy · example · what you need · steps

Why: changing a rule can remove real detections. A candidate is tested against reviewed examples and shadow scans before anyone promotes it.

Example: a candidate excludes test folders. Reviewed tests show it still flags the known vulnerable file and no longer flags the fixture; shadow scans confirm fewer matches before promotion.

You need: Rule Modify; shadow comparisons also need Assistant Source Read and Scan Results View. An administrator must configure the reviewed fixture checkout.

  1. In Rule Editing select a custom rule and choose Test improvements. The page walks through Propose → Prepare examples → Compare → Inspect shadow evidence → Decide.
  2. Change the matching fields and give a reason to save a candidate.
  3. Register versioned, secret-free fixtures with expected results, then run reviewed tests and compare.
  4. Start a shadow comparison, review it, then explicitly promote or reject the candidate. A promoted revision can be rolled back while current.

Testing uses the normal engine adapters in a bounded direct process; sandboxing is deferred. The assistant can suggest changes but cannot run tests or approve them.

library_booksApproved knowledgeWhy · example · what you need · steps

Why: so reviewed facts, such as which function sanitizes output in one library version, are cited by the assistant instead of re-explained in every chat.

Example: “OWASP Java Encoder 1.2.x: Encode.forHtml escapes HTML output”, scoped to Java and two repositories, with an accepted review as evidence.

You need: Ruleset View to read; Rule Modify to propose, approve, reject or retire.

  1. Open Knowledge from the Rules menu, or Propose knowledge from an accepted review, which fills in its rule and the review as evidence.
  2. Choose its kind, write one sentence without code or secret values, and give the language, library and versions.
  3. Pick repositories (or all repositories), optional rules and CWEs, and the evidence, by searching names.
  4. Another person with Rule Modify approves or rejects it. You cannot approve your own proposal. Retire an entry when it stops being true.

Chat cites approved entries only inside their scope. Knowledge never hides findings, changes rule health or affects what blocks a pull request.

Investigate missed issues

reportRecord a missed vulnerabilityWhy · example · what you need · steps

Why: a vulnerability the scanners did not flag is direct evidence of a gap. Recording it keeps that evidence for rule tests and searches.

Example: a pentest finds SQL injection in OrderDao.java line 42 that no rule flagged; you record the vulnerable and fixed commits.

You need: Rule Modify, Assistant Source Read, Repository Settings View and Scan Results View. Chat can stay off.

  1. Open a code repository and choose Record missed vulnerability.
  2. Enter the vulnerable full commit, affected path and line, weakness ID and evidence reference, and the fixed commit when available.
  3. Enter a versioned, secret-free fixture reference and SHA-256, language and framework, then save.

Saving a case does not run tests, change a rule or establish sanitizer behavior globally.

manage_searchFind similar code from a missed vulnerabilityWhy · example · what you need · steps

Why: one confirmed miss often means the same mistake exists elsewhere.

Example: after recording the OrderDao case, a draft rule is run across 25 repositories and finds two more files with the same pattern to review.

You need: Assistant Source Read, Repository Settings View and Scan Results View; saving tests and starting a search also need Rule Modify.

  1. Compare commits. Watchtower reads only the affected file at the vulnerable and fixed commits and shows the lines the fix changed. Nothing is saved.
  2. Save as regression tests. The vulnerable version must be flagged, the fixed version must not.
  3. Search other repositories. Choose up to 25; Watchtower runs the rule (current or a named draft) on each latest default-branch commit and lists matching lines.

Everything here is deterministic and uses no AI. Matches are places to review, not confirmed vulnerabilities, and no source code is stored.

commitUnderstand code at a pinned commitWhy · example · what you need · steps

Why: to answer “is this really reachable?” you need to read the code exactly as it was scanned, not today's branch.

Example: ask the assistant to show src/web/Login.java lines 30–60 at commit 9f2c… and list callers of authenticate.

You need: chat enabled, with Assistant Use, Assistant Source Read, Repository Settings View and Scan Results View.

  1. Open the assistant drawer, ask it to list repositories and resolve a branch once.
  2. Ask to read a path and line range, search literal text, or outline symbols and approximate references in Java, Python, JavaScript or TypeScript.

Source is downloaded temporarily for each request and deleted afterwards; credential files are excluded and excerpts are redacted. Approximate references can miss dynamic callers.

Use and administer AI

auto_awesomeAI rule assistant and ExplainWhy · example · what you need · steps

Why: to understand a rule, compare rules and read recorded feedback and health without collecting it by hand. AI is optional; every workflow above works without it.

Example: ask “Why is this rule noisy, and which reviewed findings show it?” The answer cites the rule's health and feedback.

You need: Assistant Use and enabled chat; Explain also requires Rule Modify, and evidence access uses your current source permissions.

Assistant and Explain appear for every role with Assistant Use. Until an administrator turns chat on and adds the OpenAI API key, the drawer says what is missing instead of answering.

  1. Open Explain for a rule, or open Assistant and select a model and reasoning effort.
  2. Ask what the rule detects, why it needs review, or for matching and clean examples.
  3. Use History to continue a conversation, Cancel turn to stop, and Save feedback to rate an answer.

The assistant reads authorized evidence; it cannot edit rules, run scans or promote changes. Examples are illustrative unless execution evidence says otherwise; conversations expire after the configured period, 14 days by default.

tuneAssistant settings and auditWhy · example · what you need · steps

Why: administrators decide whether chat is available, which models it may use, what it may cost and how long conversations are kept.

You need: Assistant Admin for settings; Assistant Audit separately grants audit and transcript access.

  1. Use Manage on the OpenAI row to add and test the write-only API key, then Choose model to validate synthetic compatibility and save verified pricing.
  2. Use Limits and budgets to edit conversations, answer limits and daily budgets in their dialogs. After approving a default model, turn Chat on for the initial testing group.
  3. Optionally tick AI finding assessment on (advisory second opinions) or AI theme naming on (names repeated-feedback themes in the weekly report with its own weekly budget).
  4. An auditor can use the Audit tab to inspect usage, conversation expiry, available transcripts and reported outcomes.

Secrets found by any scanner are never sent to the AI: chat sees “[REDACTED: secret detected by …]” on those lines, and feedback about rules that detect secrets is withheld. Rating an answer measures usefulness; it does not retrain the provider's model.

Before turning chat on for everyone: grant Assistant Use only to the evaluators, turn chat on, then run Answer evaluation. Score every answer from 1 to 5; it shows Ready only when every answer is in, every check passed, the average is at least 4 and none is below 3. Enabling chat for everyone stays your decision.

auto_awesomeAI proposals and reviewed ruleset changesEvidence · drafts · approval

Finding review records your judgment and handling separately. AI finding assessment is an advisory prediction, recorded separately from your judgment. Neither changes a rule or starts tests.

Open Suggest improvement from rule health, saved reviews or candidates. Select authorized evidence, generate a proposal, inspect its citations and risks, edit its matching fields, then explicitly save a draft. Illustrative examples are not reviewed fixtures. Continue in the candidate workspace with human-reviewed fixtures and explicit tests, shadowing and promotion.

Ask the assistant to manage rulesets or exact repository assignments. It can prepare a server-computed change set. Open its review link, inspect effective rule changes and every affected repository, and use Approve and apply once. Deletions require exact typed names and explicit reference replacements. Changed resources require a refreshed preview and approval. Canceled or expired drafts do not change configuration; receipts survive chat expiry.

Both journeys require Chat on, assistant readiness and current permissions. Ruleset actions also need their separate setting enabled by an Assistant Admin. Assignments never enable a scanner. No ruleset approval authorizes tests, rule promotion, future actions or agent import. Source selection and broader evidence navigation are follow-on work; no source inspection is claimed by the MVP proposal workflow.

Troubleshooting

cloudAWS Security Agent setupConnections · synthetic tests · receipts

Open AWS Security Agent setup from Configuration. Recheck reads the runtime identity, encrypted input storage, Agent Space, module policy and shared report storage. A connection check is separate from a completed scan.

Run setup test explicitly submits one packaged synthetic full, differential or clean review through the existing AWS queue. No repository code is sent. Follow the saved test result, request stop if needed, inspect retained findings and open its JSON receipt. Retries preserve the original identity; source cleanup waits for provider-terminal proof.

Use the AWS Security Agent switch under Scanner modules to turn scanning on or off. No deployment approval or scan enablement flag is needed. Include the Security review rule in the repository ruleset; no separate repository AWS settings are needed. AWS reviews and upload folders identify the repository and scan. Review records stay in AWS until manually deleted. Reports have a separate AWS findings section and a link to the AWS review. Sample-code tests are optional checks of the integration. PR enforcement is separate. AWS setup does not require Assistant Chat or its token budgets.
